## 0. 본 연구 조건 범례

이 문서에서 "native"는 두 가지 뜻으로 쓰이므로 구분해 표기한다.

- **native `E_…`**: 본 연구의 네이티브 프로토콜이다. OpenAI 호환 Chat Completions function calling이며, 결과는 `role:"tool"` content 문자열로 들어간다. 오류 필드는 없다.
- **native 플래그**: provider가 제공하는 오류 필드다. Anthropic `tool_result.is_error` 등이 여기에 해당한다. **본 연구에는 이 조건이 없다.** Chat Completions(vLLM)에서는 원리상 재현할 수 없다.

| 묶음 | 정의 위치 | 조건과 모델이 받는 문자열 |
|---|---|---|
| 텍스트 프로토콜 (reference-chatbot) | `data/conditions_v1.json`, `src/cs_common.py` `render_result` | python-sdk v1.x `simple-chatbot` 형식의 **system** 메시지 `Tool execution result: meta=None content=[…] structuredContent=None isError=<bool>`. 도구를 1회 실행한 뒤 최종 응답을 받는다. `S_ok`, `S_empty`, `E_flag_empty`(content 비어 있음, isError=True), `E_generic`(`Error: tool execution failed`), `E_perm`, `E_timeout`, `E_remedy`(`Error: request timed out. ## 1. 통합표

- 공개: 소스 공개 여부.
- isError 전달: (A)에서 모델이 받는 것. 분류는 **원문**(서버 텍스트 그대로), **JSON+isError**, **native 플래그**, **기타** 중 하나다.
- 예외: (B)에서 모델이 받는 것.
- loop: 오류 뒤 agent loop가 계속되는지. 노출 판단에 필요한 승인 기본값도 함께 적었다.
- 추가 문구: 클라이언트가 덧붙이는 remedy나 지시문.
- 가까운 조건: §0의 본 연구 조건 중 가장 가까운 것.

## 2. 요약

1. 실제 배포에서 가장 흔한 형태는 본 연구 네이티브 프로토콜의 평문 오류 조건(`E_unknown`, `E_generic`)이다. 이 조건은 원인 없는 오류 문구만 `role:"tool"`로 넘기고 플래그는 붙이지 않는다. 이 형태를 쓰는 클라이언트는 Goose, Codex, OpenAI Agents SDK, VS Code Copilot이고, OpenAI 호환 endpoint(vLLM 포함)에 붙인 LangChain(adapter ≥0.3), fast-agent, mcp-agent, Zed도 같다. Roo와 Cline v3는 여기에 `Error:\n` 접두어만 붙인다. 공식 Python 서버 SDK v2도 예상 못한 예외를 원인 없는 `Error executing tool <name>`으로 바꾸므로, 이런 오류 문구는 실험용 가공물이 아니다.
2. `E_json_flag`(isError가 든 raw JSON)도 실제로 있다. Cline v4는 이 JSON을 거의 그대로 넘기고(content가 비면 공백만 다르다), Gemini CLI는 클라이언트 설명문 wrapper 안에 넣어 넘긴다.
3. 텍스트 프로토콜은 python-sdk `simple-chatbot` 예제 하나와만 맞는다. 이 프로토콜은 system 메시지 repr을 넘기고 1 round 뒤 요약을 강제한다. 맞는 것도 v1.x repr 형식이며 v2.3.0과는 필드 이름이 다르다. 조사한 agentic 앱과 CLI는 어느 것도 이 방식을 기본으로 쓰지 않는다. provider native `is_error` 플래그(Zed·fast-agent·mcp-agent·LangChain의 Anthropic 경로 등)는 Chat Completions로 재현할 수 없어 본 연구에 대응 조건이 없다.
4. 가장 노출된 쪽은 원인 없는 오류를 원문 그대로 넘기면서 loop를 계속 도는 클라이언트다. 특히 다음 넷은 기본 설정에서 승인 단계도 없다: Goose(자동 승인, 최대 1000 turn), fast-agent의 OpenAI 경로(9999 iteration), OpenAI Agents SDK(매 turn 도구 목록을 다시 받음), mcp-agent의 OpenAI 경로. Cline v4와 Continue CLI는 isError를 성공으로 처리하므로 오류가 반복돼도 멈추는 장치가 작동하지 않는다. Zed, Copilot, Roo, Cline v3, Codex도 같은 형태로 오류를 넘기지만, 기본 설정에서 호출마다 사용자 확인을 받는다.
5. 가장 덜 노출된 쪽은 오류 뒤의 다음 행동을 구조적으로 막는 클라이언트다.
   - `simple-chatbot`: 두 번째 응답을 파싱하지 않는다.
   - MCP 튜토리얼: 두 번째 응답의 tool_use를 버린다.
   - Pydantic AI: 같은 도구에서 오류가 두 번 나면 run을 끝낸다.
   - adapter ≤0.2.2와 LangGraph prebuilt ≥1.0.2 조합: 첫 isError에서 graph를 중단한다.
6. remedy 비슷한 문구를 이미 붙이는 클라이언트는 다음과 같다.
   - Pydantic AI: isError 기본 경로에 "Fix the errors and try again."
   - Continue IDE: isError와 예외 모두에 "Please try something else or request further instructions."
   - LangGraph ToolNode `handle_tool_errors=True`(prebuilt ≤1.0.1 기본): "Please fix your mistakes."
   - OpenAI Agents SDK: 예외에만 "Please try again."
   - VS Code Copilot: 예외에만 "Please check your input and try again."
7. 어느 클라이언트도 isError 결과에 본 연구 `E_remedy`·`E_unknown_remedy`의 "Retry the same request." 같은 같은-호출 반복형 문구를 붙이지 않는다. 실제 문구 대부분은 행동을 바꾸라는 쪽이다. 그래서 remedy 조건의 결과를 이 클라이언트들의 노출 감소로 그대로 옮길 수 없다. 행동 수정형 문구가 poisoned rule을 "고칠 방법"으로 읽게 만들 가능성도 있지만, 이것은 시험하지 않은 가설이다.
8. 위 판단은 모두 소스에서 조립한 [DERIVED] 텍스트에 근거하며, 실행해 확인하지는 않았다. Claude Code, Claude Desktop, Cursor는 소스가 비공개라 전달 형식 대부분이 UNVERIFIED다.

**English draft (for the paper):**
The most common deployed form of a failed MCP call is an unexplained error string passed verbatim as a plain `role:"tool"` message with the isError flag dropped. This is our native-protocol `E_unknown`/`E_generic` condition. Goose, Codex, the OpenAI Agents SDK, VS Code Copilot, and the OpenAI-compatible paths of LangChain (adapters ≥0.3), fast-agent, mcp-agent, and Zed all deliver errors this way, and the official Python server SDK v2 itself emits the cause-free `Error executing tool <name>` for unexpected exceptions. The raw-JSON condition `E_json_flag` also occurs in the wild: Cline v4 forwards `{"content":[…],"isError":true}` almost verbatim, and Gemini CLI wraps the same JSON in a neutral client sentence. In contrast, our text protocol (a system-role repr followed by a forced single-round summary) matches only the python-sdk `simple-chatbot` example, and only its v1.x repr format; none of the surveyed agentic apps or CLIs does this by default. Provider-native `is_error` flags (Anthropic and Bedrock) cannot be expressed over Chat Completions, so our study has no matching condition for them. The most exposed clients forward the unexplained text and keep the agent loop running, and several also skip user approval by default: Goose (auto-approve, up to 1000 turns), fast-agent and mcp-agent on OpenAI-compatible endpoints, and the OpenAI Agents SDK. Cline v4 and Continue CLI even treat isError as success, so their repeated-failure stops never fire. The least exposed clients cut the loop after an error: `simple-chatbot` and the MCP tutorial do not act on a second response, Pydantic AI aborts on a second error from the same tool, and adapters ≤0.2.2 with LangGraph prebuilt ≥1.0.2 abort on the first isError. Several clients already append remedy-like text: Pydantic AI ("Fix the errors and try again.", on isError by default), Continue IDE ("Please try something else or request further instructions."), LangGraph ToolNode with `handle_tool_errors=True` ("Please fix your mistakes."), and, on exceptions only, the OpenAI Agents SDK ("Please try again.") and Copilot ("Please check your input and try again."). None of them appends a repeat-the-same-call remedy such as our "Retry the same request." to isError results, so our remedy results do not transfer directly to these clients. All model-facing strings were reconstructed from source code, not observed at run time, and the closed-source clients (Claude Code, Claude Desktop, Cursor) remain largely unverified.
